# Permissions and privacy

Owner: WA-R05, WA-R13. Data ownership: [data model](DATA_MODEL.md). Source restrictions: [ERPNext integration](ERPNext_INTEGRATION.md).

## Role policy

- **Marketing User:** manage permitted contact profiles, tags, imports, segments and local template drafts; prepare/test campaigns and request approval. Read permitted campaign outcomes. Cannot approve, launch, publish automations, view secrets or access the inbox without an agent role.
- **Marketing Manager:** Marketing User capabilities plus campaign approval/lifecycle actions, automation editing/publication, company inbox management, suppression administration and authorised reports/exports. No credential access by default.
- **WhatsApp Agent:** assigned or authorised User Group conversations, minimal associated contact details, internal notes, replies, permitted assignments, opt-out recording and handover. Cannot browse the entire marketing address book or change campaigns.
- **Marketing Analyst:** company-authorised aggregate reports/cards only. No message content, consent evidence, raw technical events, credentials or contact exports by default.
- **System Manager:** connection/settings administration and diagnostics within configured company. Access to inbox/content still follows explicit business permissions; administrative framework capabilities are privileged and audited rather than promised to be technically impossible to override.

Implement DocPerms, field permission levels, permission query conditions and document-level checks together. Query conditions protect lists; document checks protect direct lookups. Commands additionally verify action-specific roles and current state. User/company restrictions apply on all paths. Never rely on Sidebar visibility or client-only filters.

Agents may see unassigned conversations only when in that conversation's configured team; otherwise managers assign them. Existing conversation access does not grant access to every linked ERPNext record. Internal notes use the same conversation scope.

## Consent policy

Use affirmative marketing evidence with notice version, source and occurrence time. CRM membership/import is not permission. Record withdrawals immediately before ordinary keyword handling. Regrant requires evidence newer than withdrawal; replayed/backdated grant events cannot reopen sending. Apply suppression across company numbers.

The design follows Meta's permission/template/opt-out constraints and uses explicit affirmative marketing consent as the product default. Keep human escalation available and distinguish permitted inbound support from promotional campaigns. Review the [current policy](https://business.whatsapp.com/policy) before release.

For South Africa, preserve sender identification, withdrawal and evidence workflows in accordance with the configured POPIA policy. Do not claim that software alone guarantees legal compliance or that a Customer record supplies the existing-customer exception. [Information Regulator guidance](https://inforegulator.org.za/popia/)

## Credential and media boundaries

Connection access tokens, app secrets and verification tokens are Frappe Password fields with server-only retrieval. Redact request headers, tokens, payload query strings and personal data in logs. Rotation invalidates readiness and is audited; webhook signing-secret rollover follows the verified Meta contract, never indefinite acceptance of old secrets.

All media/evidence/import/export files are private and attached to the owning authorised record. Download permission checks the current actor and owner. Do not trust a caller-supplied File URL or copy a private URL into a public field.

Inbound media downloads use validated provider media IDs and provider hosts from the supported contract, with redirect/host controls, size bounds and MIME/content checks. V1 outgoing types: JPEG/PNG up to 5 MB, PDF up to 10 MB, further restricted by the verified provider limit. Reject executable/HTML/SVG attachments; unsupported inbound content receives a safe placeholder and an operator diagnostic. Never render customer content as HTML. Store quarantined failures privately; do not offer download until validated.

## Realtime, reports and export

Publish only invalidation IDs/progress to authorised document/user channels after commit; never broadcast conversation bodies to the site. Assignment changes revoke access on the next API call; realtime content must not persist in a room after reassignment. UI refetches from permission-checked endpoints and removes inaccessible conversations.

Reports apply company/document restrictions before aggregation. Number Cards cannot reveal unrestricted counts. Exports require explicit export permission, are generated by a reauthorised worker and are retrieved as private files. Avoid CSV formula injection by escaping dangerous spreadsheet-leading values in exports.

## Retention and data subject actions

An administrator must configure positive retention periods and a policy reference before live enablement. No default period is presented as a legal requirement. Cleanup covers raw events, message content, media, operation files and consent evidence separately; legal holds suspend deletion.

On approved erasure: redact content and permitted profile data, preserve necessary integrity metadata and a minimised keyed suppression identity under the configured policy so erased people are not re-imported and marketed to. A request to remove all suppression information needs explicit policy review, not automatic unrestricted deletion. Export/erasure jobs verify requester authority and current access.

Document audit actions for credentials/readiness, consent, suppression, campaign approval/changes, publication, assignment, sending switches, exports, retention and unknown-result reconciliation. Append-only audit content excludes secrets and unnecessary message text.

Verification: [WA-A03, WA-A04, WA-A09, WA-A14, WA-A17](TESTING_AND_ACCEPTANCE.md).


## Foundation access and staged availability

P1-001 ships read-only feature metadata and editable System Manager settings; it does not enable later feature commands. [Permission adapters](../../tag_marketing/infrastructure/permissions.py) apply configured-company boundaries and native Company User Permissions to lists and direct IDs. Inbox reads additionally require Marketing Manager or assignment/team-authorised WhatsApp Agent access; read cursors remain user-specific. System Manager alone receives connection/settings and technical diagnostics, not contact or inbox content. Analysts receive no raw-record DocPerms; their aggregate interfaces belong to P7. Raw webhook payloads have no business-role field grant.

Source-bearing contact/campaign/snapshot/recipient/import-row projections and operation results stay unreadable through generic record access until their owning feature tasks implement source/target reauthorisation. Operation progress queries belong to P1-003. Agent contact summaries belong to P5; no full-address-book grant is added as a shortcut. This staged denial is an implementation gate, not a change to the final role policy above.

Owned records cannot use DocShare: the [pinned framework](../../../frappe/frappe/model/db_query.py) can let a share override normal document and list permission denials. An owned DocShare validation hook rejects such grants, including privileged generic inserts; migration stops if unsupported existing shares are found rather than deleting administrator data silently. Assignment/team and company rules remain the supported access mechanism. Privileged direct SQL remains outside ordinary user authorisation.
